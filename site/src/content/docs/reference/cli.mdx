`snitchhiker` talks to the running daemon over `/run/snitchhiker/admin.sock`, which only root can open: run it with `sudo`. The exception is `snitchhiker mcp`, which an agent runs as you, on the agent socket ([Agents](/guides/agents/)). It is the daemon's own binary, run under another name.

```text
snitchhiker <command> [options]
```

<Code code={help} lang="text" title="snitchhiker --help" />

## `status`

The daemon's version, mode and policy, and its counters: rules in effect, connections decided since it started, history entries dropped because the database couldn't keep up, prompts waiting, and connected clients (this command's own connection included).

## `policy`

| Command | |
| --- | --- |
| `policy` | The [policy](/reference/configuration/#the-policy-changed-while-the-daemon-runs) in effect, marking the settings a client changed |
| `policy set <setting>=<value>...` | Change settings while the daemon runs: `mode=enforce\|monitor`, `no_match=ask\|allow\|deny\|reject`, `no_client=…`, `on_timeout=…` (`allow`, `deny`, `reject`), `prompt_timeout_secs=<1–3600>`, `retention_days=<1–3650>` |
| `policy reset [<setting>...]` | Return settings (all, without names) to `daemon.toml`'s |

## `alerts`

| Command | |
| --- | --- |
| `alerts [--all]` | Alerts not acknowledged yet; `--all`: the newest 50 of any state |
| `alerts ack <id>...`, `alerts ack --all` | Acknowledge alerts, for every client |
| `alerts rules` | The [alert rules](/guides/alerts/#alert-rules) |
| `alerts rules add <name> [--query <q>] [--threshold <n>] [--window <secs>] [--first-program]` | Add one |
| `alerts rules rm <id>` | Delete one |

## `system`

| Command | |
| --- | --- |
| `system` | The [system firewall](/guides/system-firewall/): on or off, its policies and rules |
| `system on`, `system off` | Turn it on or off |
| `system input <accept\|drop>`, `system forward <accept\|drop>` | Its policies |
| `system export`, `system import <file> [--trial <secs>]` | As TOML; with `--trial`, an import reverts by itself unless confirmed |
| `system confirm` | Keep a change made with `--trial` |

## `rules`

| Command | |
| --- | --- |
| `rules` | List the rules: id (`-` for locked ones), action, tier, folder path and name, and conditions |
| `rules add <allow\|deny\|reject> [conditions] [--name <n>] [--tier <override\|normal\|fallback>]` | Add a rule |
| `rules rm <id>` | Delete a rule |
| `rules move <id> <folder>` | Move a rule to a folder (`0`: the top level) |
| `rules enable <id>`, `rules disable <id>` | Switch a rule on or off |
| `rules edit <id,id,...> <change>` | Change many rules as one batch (one undo): `enable`, `disable`, `delete`, `move <folder>`, `action <allow\|deny\|reject>`, `expires <hour\|half-day\|until-restart\|never>` |
| `rules lint [--days <n>]` | The [rules check](/guides/rules/#checking-the-rules); with `--days`, also rules that decided nothing in that many days |
| `rules import <file>` | Add the rules of a [rule file](/reference/rule-files/) to a top-level folder (named by the file's `[folder]`, or after the file), made if there is none; rules whose name the folder already has are left out, so an import repeated adds nothing twice |
| `rules export` | Print the stored rules as a rule file |
| `rules import-opensnitch [<dir>] [--dry-run]` | Import OpenSnitch's rules (default `/etc/opensnitchd/rules`) into a folder `OpenSnitch`; see [Moving from OpenSnitch](/guides/opensnitch/) |

Locked rules (the System folder and the files in `rules.d`) can't be deleted, switched or changed from here.

Conditions of `rules add`, all of which must hold; repeat an option for alternatives:

| Option | |
| --- | --- |
| `--exe <path>` | The executable: a path, `glob:…` or `re:…` ([patterns](/guides/rules/#text-patterns)) |
| `--host <name>` | A host name, or `*.` and a domain |
| `--net <cidr>` | An address, a range, or an alias (`loopback`, `lan`, `multicast`, `imds`, `cgnat`) |
| `--port <n[-m]>` | A port or a range |
| `--uid <n>` | A user id |
| `--protocol <tcp\|udp\|icmp\|icmpv6\|n>` | The IP protocol |
| `--app <identity>` | The program's identity: `pkg:<package>`, `nix:<name>`, `unit:<service>`, `snap:<name>` |
| `--sha256 <hex>` | The executable's SHA-256: that binary only |
| `--writable <true\|false>` | Whether a user other than root can change the executable |
| `--container <name>`, `--image <reference>`, `--compose <project/service>`, `--container-id <id>` | In that container only ([Containers and VMs](/guides/containers/)) |
| `--vm <name>`, `--netns <name>` | In that VM, or named network namespace, only |
| `--list <name>` | The destination is on that [blocklist](/guides/blocklists/) |
| `--any-context` | Also for processes in containers and other namespaces |

```bash
sudo snitchhiker rules add allow --exe /usr/bin/ssh --port 22 --name SSH
sudo snitchhiker rules add deny --host '*.example.net' --tier override
```

## `folders`

| Command | |
| --- | --- |
| `folders` | List the folders, with their path and how many rules each holds |

## `explore`

```text
snitchhiker explore [--by <program|host|port|user|container>] [--hours <n>] [--where <dimension>=<value>] [--bytes] [--compare]
```

The connections of the last `n` hours (24 by default), grouped by program (the default), host, port, user or container, busiest first (by bytes with `--bytes`: the top talkers), with how many were allowed and blocked and their bytes. `--where` narrows them to one program, host (empty: no name), port or user: `--by host --where program=/usr/bin/curl` lists where curl connects. `--compare` adds the period before, and marks what is new in this one. The answer comes from hourly rollups, so it takes as long for a month of history as for an hour.

## `connections` and `kill`

```text
snitchhiker connections
snitchhiker kill <tcp|udp> <local address:port> <remote address:port>
```

`connections` lists the live TCP connections and connected UDP sockets: state, local and remote ends, user, program (`?` for sockets whose opening the daemon didn't see: inbound ones, and ones older than the daemon), the name the program looked up for the remote end, and bytes. `kill` closes one as a reject does: the program's next call on it fails with `ECONNABORTED`.

## `history` and `undo`

```text
snitchhiker history [--limit <n>]
snitchhiker undo <change>
```

`history` lists the changes to rules and folders, newest first (50 by default): id, batch, time, who made it (`cli`, `desktop`, `android`, a prompt answered from one of them, an agent's approved proposal or envelope, `docker` or `podman` for a removed container's rules) and what changed. `undo` undoes every change of a change's batch, as a new batch; it is refused when something it would put back was changed again since. See [Rules](/guides/rules/#history-and-undo).

## `events`

```text
snitchhiker events [--limit <n>] [--query <query>] [--follow]
```

The newest connections (50 by default): sequence number, action, user, program, destination (the name the program looked up, or the address), port, protocol, and the bytes sent and received so far. With `--query`, only those the [query](/reference/query-language/) matches, looked for among the newest 50 000. With `--follow`, connections are printed as they are decided (only those the query matches) until interrupted: `snitchhiker events --follow --query action:deny` shows what is blocked as it happens.

## `stats`

```text
snitchhiker stats [--hours <n>]
```

The last `n` hours (24 by default) at a glance: how many connections were allowed and blocked, the bytes sent and received, and the ten busiest programs and hosts. It reads the same rollups as [`explore`](#explore).

## `explain`

```text
snitchhiker explain <seq>
```

Why a recorded connection (by its sequence number, from `events`) is decided as it is: every rule that matches it under the rules in effect now, in precedence order, the deciding one first, with each rule's action, tier and specificity. With none, the connection would be prompted for, or decided by `no_match`. Rules on command lines or parent processes can't be checked, since the history doesn't keep those; the answer says so when such rules exist. The desktop app's Events page has the same as the info button on each row (or a double-click on it).

## `learn`

```text
snitchhiker learn [--hours <n>] [--folder <name>]
```

Prints a rule file with a rule for each program, destination and port that no rule decided in the last `n` hours (default 24), in a folder named `name` (default "Learned"). Program paths are generalised as in [prompts](/guides/prompts/#what-a-prompt-offers). Connections from a container, a VM or a named network namespace get rules for that place only (a container by its Compose service, name or image). Review it, then `rules import` it.

## `prompts`

| Command | |
| --- | --- |
| `prompts` | The prompts waiting for an answer, each with its numbered suggestions |
| `prompts watch` | Print prompts as they open and as they are resolved, until interrupted. While it runs, the daemon has a client to ask |
| `prompts answer <id> <allow\|deny\|reject> [--suggestion <n>] [--duration <d>] [--folder <id>]` | Answer a prompt with a rule made from suggestion `n` (default 0, the narrowest), in the program's folder (`Apps/<program>`) or the folder given |

Durations: `once` (no rule), `restart`, `hour`, `12h`, `forever` (default). See [Prompts](/guides/prompts/#answering).

## `lists`

The [blocklists](/guides/blocklists/): `lists` shows them with their entries and what they decided, `lists add <name> <source>` adds one (an `https://` URL, or a file directly in `/etc/snitchhiker/lists/`), `lists refresh` fetches one now, `lists rm` deletes one.

## `contexts`

The containers, VMs and named network namespaces connections came from in the last hours, with their connections and bytes; with a name, that one's programs. See [Containers and VMs](/guides/containers/).

## `proposals` and `envelopes`

Coding agents' [proposals](/guides/agents/#reviewing): list, show, approve or deny them (`--mute` stops an agent's later ones). Envelopes approve proposals within bounds without asking; adding or removing one is a dangerous action. See [Agents](/guides/agents/#envelopes).

## `pair`, `devices` and `approvals`

`pair` prints a one-time code, link and QR code for a phone or another machine's app ([Pairing a device](/guides/remote/#pairing-a-device)); `--role viewer` pairs one that can't change anything. `devices` lists the paired devices, and `devices rm` unpairs one. `approvals` lists the dangerous actions remote devices asked for, waiting for someone here; `approvals approve` or `deny` decides one.

## `mcp`

The MCP server coding agents start (as you, not with `sudo`): see [Agents](/guides/agents/).

## `audit`

```text
snitchhiker audit [--limit <n>]
```

The dangerous actions clients asked for, newest first (50 by default): id, time, outcome (`authorized`, `refused`, or `unchecked` for root's requests and with step-up off), client, user, process, and what was asked. See [Security](/internals/security/#dangerous-actions-need-more-than-a-session).

## `version`

Prints the version.

## `snitchhikerd`

```text
snitchhikerd [--config <path>]
snitchhikerd [--config <path>] trust-client <path>
snitchhikerd [--config <path>] untrust-client <path>
snitchhikerd [--config <path>] trusted-clients
```

<Code code={daemonHelp} lang="text" title="snitchhikerd --help" />

The daemon, started by its systemd unit. `--config` reads another [configuration](/reference/configuration/) file than `/etc/snitchhiker/daemon.toml`. `SIGHUP` (`systemctl reload snitchhikerd`) reads the rules again; `SIGTERM` and `SIGINT` stop it. Logs go to the journal; `RUST_LOG` sets their level (`info` by default).

### Trusted clients

`trust-client` registers a client binary for the client socket, pinned to its SHA-256; run it again after the binary is upgraded (packages do it from their install hook). The binary must be owned by root, in directories only root can write to, and setgid to `client_group`. `untrust-client` removes it, and `trusted-clients` lists the registered binaries and those in [`trusted_clients`](/reference/configuration/#trusted_clients).

The registry is a file next to the database, read whenever a client connects: changes apply to the next connection, and the daemon needn't be running. See [Security](/internals/security/#clients).

## `snitchhiker-remote`

```text
snitchhiker-remote [--config <path>]
snitchhiker-remote seal-key [--config <path>]
snitchhiker-remote client
```

[Remote access](/guides/remote/), from the `snitchhiker-remote` package. Without a command it is the node's endpoint, started by its systemd unit (`snitchhiker-remote.service`, as the `snitchhiker-remote` user): `--config` reads another file than [`/etc/snitchhiker/remote.toml`](/reference/configuration/#remotetoml). `SIGTERM` and `SIGINT` stop it; it also ends when the daemon does. Logs go to the journal; `RUST_LOG` sets their level.

`seal-key` (as root) seals the node's key with `systemd-creds`, to the TPM or the host's key, and deletes the plaintext; the service imports it from its next start ([Where the keys are](/guides/remote/#where-the-keys-are)).

`client` is the desktop app's helper: the app starts it to reach remote nodes. It isn't meant to be run by hand.
