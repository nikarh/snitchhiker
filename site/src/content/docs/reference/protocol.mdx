Every client of a node, the command line included, speaks one protocol: length-prefixed [Protocol Buffers](https://protobuf.dev) messages over a stream. This page specifies it; the [schema](#schema) at the end is the source of truth for every message and field.

## Transport

Local clients connect to a unix stream socket of the node:

| Socket | For | Role |
| --- | --- | --- |
| `/run/snitchhiker/admin.sock` | processes running as root | `ROLE_ROOT` |
| `/run/snitchhiker/client.sock` | Snitchhiker's verified client binaries ([Security](/internals/security/#clients)) | `ROLE_ADMIN` |

Remote clients (the Android app, later) will reach nodes over an encrypted peer-to-peer connection that carries the same frames.

## Framing

```text
preamble, once, client → node:   "SNHK"  major (uint16 LE)
every frame after it, both ways: length (uint32 LE)  message
```

- The **preamble** opens a local connection: the four bytes `SNHK`, then the major protocol version as a little-endian 16-bit integer (`1`).
- Every **frame** is a little-endian 32-bit length, then that many bytes of one Protocol Buffers message: a `ClientFrame` from client to node, a `ServerFrame` from node to client.
- A frame is at most 16 MiB. A peer that receives a longer length closes the connection.

## Handshake

1. The client sends the preamble. A node that doesn't speak that major version answers with a `Refusal` saying which it speaks, and closes.
2. The client sends a `ClientFrame` with `Hello`: its minor version, what it is (`cli`, `desktop`, `mcp`, `android`) and its version.
3. The node answers `Welcome`: its minor version, its daemon version and name, its capabilities, and the **role** of this connection. A connection that isn't allowed gets a `Refusal` instead, and the node closes it.

A client must not send requests before it has the `Welcome`.

## Roles

| Role | May |
| --- | --- |
| `ROLE_ROOT` | everything |
| `ROLE_ADMIN` | everything a client app needs: read, answer prompts, change rules |
| `ROLE_VIEWER` | read only: `GetStatus`, `ListRules`, `ExportRules`, `ListEvents`, `ListPrompts`, `ListAudit`, `Subscribe`, `Unsubscribe` |
| `ROLE_AGENT` | the agent socket's, for [agents](/guides/agents/): `GetStatus`, `CheckConnection`, `RecentBlocked`, `ProposeRules`, and `GetProposal`, `WithdrawProposal` and `AnnotatePending` for its own proposals and prompts. It changes nothing |

A request the role doesn't allow gets an `ERROR_CODE_FORBIDDEN` error. Rules that can't be changed through the protocol (the System folder, root's `rules.d` files) are listed with `locked` set, and changing one gets `ERROR_CODE_LOCKED`.

## Requests and responses

A `Request` carries a client-chosen `id` and one method. The node answers each with a `Response` with the same `id`, holding either the method's result or an `Error` (a code and a message for people). A client may send several requests without waiting; responses carry their request's id, and notices can arrive between them.

| Method | Result | |
| --- | --- | --- |
| `GetStatus` | `Status` | Mode, policy and counters |
| `ListRules` | `RuleList` | Every folder and rule, locked ones included |
| `AddRule` | `RuleAdded` | Stores a rule; returns its id |
| `DeleteRule` | `Done` | |
| `UpdateRule` | `Done` | Replaces a stored rule; an allow-everything rule needs step-up |
| `AddFolder` | `FolderAdded` | |
| `UpdateFolder` | `Done` | Its name, parent, enabled and scope; a folder can't go inside itself |
| `DeleteFolder` | `Done` | With the folders below it and their rules; more than 20 rules needs step-up |
| `ListChanges` | `ChangePage` | The history of rules and folders, newest first |
| `ListConnections` | `ConnectionList` | The live connections, with their programs |
| `KillConnection` | `Done` | Closes a live socket, as a reject does |
| `Explore` | `ExplorePage` | Connections of a time range grouped by program, host, port or user, optionally of one value of another, busiest first |
| `Undo` | `Done` | Undoes a change's batch, unless changed again since |
| `SetRuleEnabled` | `Done` | |
| `ListAudit` | `AuditPage` | Dangerous actions asked for, newest first: `limit` entries with `id` below `before` (0: from the newest) |
| `ImportRules` | `Done` | A [rule file](/reference/rule-files/) as TOML, into a new folder; checked as a whole first |
| `ExportRules` | `RuleFile` | The stored rules as a rule file |
| `Learn` | `RuleFile` | Rules for the connections no rule decided in the last hours |
| `ListEvents` | `EventPage` | History, newest first: `limit` entries with `seq` below `before` (0: from the newest) |
| `ListPrompts` | `PromptList` | Prompts waiting for an answer |
| `AnswerPrompt` | `Done` | Decides a prompt, with the rule made from a suggestion or from the client's conditions. The rule's id comes in the `PromptResolved` notice |
| `CheckConnection` | `CheckedConnection` | How a connection would be decided by today's rules (agent) |
| `RecentBlocked` | `BlockedList` | The connections of the agent's own processes refused or asked about in the last hour (agent) |
| `ProposeRules` | `Proposal` | Rules for a person to approve, shaped by the node (agent) |
| `GetProposal` | `Proposal` | A proposal; with `wait_secs`, answered once it is no longer pending (or the time is up) |
| `WithdrawProposal` | `Proposal` | (agent) |
| `AnnotatePending` | `Done` | A note on a prompt the agent's own process opened (agent) |
| `ListProposals` | `ProposalList` | Proposals, newest first |
| `DecideProposal` | `Proposal` | Approves (with the rules as edited, for a duration) or denies, with a reason the agent is told; a marked rule needs step-up |
| `Subscribe` | `Subscribed` | Starts a subscription; returns its id |
| `Unsubscribe` | `Done` | |

A node that doesn't know a method (an older node) answers `ERROR_CODE_UNSUPPORTED`. A dangerous request (a rule that allows every program to connect anywhere) from a client needs polkit's authorization of the client's process, which the node asks for while the request waits; without it the answer is `ERROR_CODE_NOT_AUTHORIZED` ([Security](/internals/security/#dangerous-actions-need-more-than-a-session)).

Addresses are bytes: 4 for IPv4, 16 for IPv6. Times are Unix milliseconds.

## Subscriptions

`Subscribe` to a topic, and the node pushes a `Notice` with the subscription's id for each thing that happens, until `Unsubscribe` or the connection closes:

| Topic | Notices |
| --- | --- |
| `TOPIC_PROMPTS` | `Prompt` as each opens, `PromptResolved` as each is answered (by anyone) or times out |
| `TOPIC_EVENTS` | `ConnectionEvent` for every connection as it is recorded, with its `seq` |
| `TOPIC_RULES` | `RulesChanged`: list the rules again |
| `TOPIC_ALERTS` | `Alert` as each is raised, `AlertsChanged` when alerts are acknowledged |
| `TOPIC_PROPOSALS` | `Proposal` as each is made and whenever its state changes; subscribing sends those waiting first |

A subscription to `TOPIC_PROMPTS` is also what makes a node ask: with no subscriber, `no_client` decides instead of a prompt.

### Resuming

A client that loses its connection resumes where it was:

- **Events.** It subscribes with `after` set to the `seq` of the last event it saw. The node first sends the stored events after it, oldest first, then the live ones, with nothing in between lost. At most 4000 are sent this way; further behind, the answer is `ERROR_CODE_INVALID`, and the client pages with `ListEvents` before subscribing from the newest.
- **Prompts.** Subscribing sends a `Prompt` for each prompt waiting, then the new ones.

Around the moment of subscribing, an event or a prompt may arrive twice: clients ignore events whose `seq` they have seen and prompts whose `id` they know.

Each connection has a bounded queue of outgoing frames. A client that doesn't read fast enough misses notices rather than slowing the node down. The next notice it gets has `missed` set, and the client resumes as above, or lists prompts and rules again.

## Columnar blocks

Bulk event data (a page of history, live events) can travel as one columnar block instead of one `ConnectionEvent` per event: `ListEvents` with `columnar` answers with an `EventBlock`, and a subscription to `TOPIC_EVENTS` with `columnar` gets an `EventBlock` notice per batch the node records (about every 100 ms; a backfill is one block). In the [benchmark](https://github.com/nikarh/snitchhiker/blob/main/docs/decisions/0007-wire-format.md) a block is about a third smaller than the same events as messages, and an order of magnitude faster to read: the columns are arrays of fixed-width little-endian values, read in place, without decoding each event.

```text
offset  size   field
     0     4   magic "SNEB"
     4     2   format version (1)
     6     2   columns in the directory (n)
     8     4   rows
    12     4   reserved, 0
    16     8   base seq (i64)
    24     8   base time (u64, Unix ms)
    32   8×n   directory: per column its id (u16), the width of one value (u16), its offset from the block's start (u32)
     …         the columns, each rows × width bytes
```

All numbers are little-endian, and nothing needs alignment. A reader finds columns by id and skips ids it doesn't know, so later formats can add columns; a known column with another width is an error. The columns of format 1:

**Strings travel once.** Blocks refer to programs and host names by the node's interned string ids, stable for its epoch. The `dictionary` of an `EventBlock` holds the ids it uses that this connection hasn't been sent before, with their strings: a client keeps one dictionary per node and adds to it from every block. The node decides a block's dictionary as it queues the block, so a client never receives an id before its string.

Remote connections will also compress bulk data with zstd, in streaming mode; local sockets don't. Why blocks rather than FlatBuffers or rkyv: [decision 0007](https://github.com/nikarh/snitchhiker/blob/main/docs/decisions/0007-wire-format.md).

## Versioning

The protocol has a major and a minor version.

- **Within a major version, changes are additive only.** Fields, messages, enum values and methods are added; none is renumbered, renamed, retyped or removed. A removed field's number and name become `reserved`.
- Unknown fields are ignored, and every enum's zero value is `*_UNSPECIFIED`, so an older peer reads a newer one's messages.
- The **minor** version in `Hello` and `Welcome` says what each side knows; a client uses a newer method only when the node's minor version has it, and handles `ERROR_CODE_UNSUPPORTED` anyway.
- Anything else is a new **major** version, under a new package (`snitchhiker.v2`), named in the preamble. A node may speak several.

Version 1.0 is the current version. CI lints the schema and checks every change against `main` with [buf](https://buf.build): renumbering, renaming, retyping or removing anything fails it.

## Conformance vectors

[`proto/vectors/v1/`](https://github.com/nikarh/snitchhiker/tree/main/proto/vectors) holds frames for checking an implementation of the protocol: each is a message in protobuf text format (`.textproto`, naming its type on its first line) and the frame as sent, in hex (`.hex`). An implementation must decode every frame to its message, and encode every message to exactly its frame, apart from the vectors marked `# decode-only`. Those carry what a newer peer may send, an unknown field and an unknown kind of frame, which a decoder must skip.

`00-preamble.hex` is the preamble, and `blocks/` holds columnar blocks in hex with their rows as text. Frames and blocks, once published, never change: a change to how an existing one encodes is a breaking change.
