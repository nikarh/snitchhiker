Crate snitchhiker_daemon

The daemon’s parts, as a library: the binary (main.rs) wires them together, and the end-to-end scenarios exercise them in the test VMs.

Modules§

agents
Agents (decision 0008): who an agent is, what its own processes were refused, and its proposals.
alerts
Alerts: raised by the node about itself, and by the user’s alert rules over the connections recorded. Every alert is kept, published to the clients subscribed to alerts, and logged (to the journal, under systemd).
api
The daemon’s local API: the client socket (the desktop app, the MCP server: verified by the kernel, see peer) and the admin socket (root, the command line), both speaking the client protocol (snitchhiker-proto).
approvals
Step-up from another device (plan §4.3, M5): a dangerous action a remote device asks for waits for a local admin (the desktop app on the node, confirmed by polkit, or root) to approve it. A remote device can’t approve: it has no local process for polkit to check.
apps
Stable identities of programs (process.app): names that survive updates and moves, from facts only root (or the package manager, Nix or snapd) can set:
blocklists
Blocklists from URLs and files (plan §5.8): fetched on a schedule, checked before they replace what was there, kept on disk so a restart without a network still has them, and named by rules’ list condition.
cleanup
snitchhikerd cleanup: what happens to the daemon’s tables after it stopped (the service runs it after every stop, ExecStopPost, with systemd’s SERVICE_RESULT saying how the stop went).
cli
The command line (snitchhiker): a client of the running daemon over its admin socket (root only, so sudo).
config
/etc/snitchhiker/daemon.toml: what root decides about the daemon. Clients can’t change any of it.
container_events
Containers’ lifecycle from their runtimes’ event streams (Docker’s API, and rootful Podman’s, which speaks it):
contexts
Who a container’s connection comes from (plan §5.10): the runtime and container its process’s cgroup names, with the container’s name, image, labels and Compose service from the runtime itself. Exact or nothing: a field that can’t be read stays empty, and rules on it don’t match.
dns
Names of addresses, learned from the DNS answers processes receive.
fallback
The owner of a flow the attribution programs didn’t record (a protocol path they don’t hook, a socket opened before the daemon started): the kernel’s socket for exactly that flow (sock_diag), then the one process holding that socket. Several different processes holding it (a socket passed on, or kept across a fork) leave the program unknown: which of them sent the packet can’t be told.
forward
Forwarded traffic (plan §5.10): a container on a bridge network, or a VM on a tap, sends packets that are forwarded from its bridge port; they never pass the host’s output hook. Their sender is found exactly:
guard
What a change to the policy or system firewall loosens, judged on the state it leaves rather than on the request: any path to the same state is audited alike. A local client needs no step-up for it (decision 0019); a remote device waits for a local approval.
hub
Subscriptions: which connection wants which topic, and pushing notices to them.
learn
Turning what the daemon saw (connections no rule decided) into rules to review: one rule per program, destination and port, where it came from, with the program’s path generalised so updates don’t break it. A container’s connections get rules for that container (its Compose service, else its name, else its image), a VM’s for that VM, a named namespace’s for it: a rule learned from a container never applies to the host.
lint
The lint and dedupe report on this node: the rule set (the database’s and the managed ones), what the filesystem says about their binaries, and when each rule last decided a connection.
locked
The store behind a lock that knows which thread holds it. A thread locking it again while holding it would wait for itself forever (a second daemon.store() in an expression whose first guard is still alive is easy to write); here that panics, saying where, instead of hanging the daemon.
logind
Whether a user is at the machine, from logind: one of their sessions is active, not locked and not idle. For prompt routing (router), called from its own thread.
managed
Rules that aren’t edited through Snitchhiker: the built-in System folder, and the files root keeps in rules.d/ (provisioning: a fleet’s baseline from Ansible or cloud-init). They are read at start and on every reload, live only in memory, and are locked: clients can see them, not change them.
mcp
snitchhiker mcp: an MCP server (stdio) for coding agents, speaking to the node’s agent socket (decision 0008).
namespaces
Network namespaces the daemon decides inside (plan §5.10).
notify
Telling systemd the daemon is ready (Type=notify): the sd_notify datagram, without libsystemd.
peer
Who is on the other end of a unix socket, from facts only the kernel and root can establish, and whether it is one of Snitchhiker’s own client binaries.
placement
Where a rule made by answering a prompt goes: the folder the client chose, or the program’s own folder.
policy
The node’s policy: the settings of daemon.toml that clients may change while the daemon runs (mode, what happens to connections no rule decides, prompts’ timeouts, how long history is kept). What clients changed is kept in the database, recorded in the history like rule changes, and takes precedence over the file; a reset returns a setting to the file’s.
process
What the daemon knows about the process behind a connection, read from /proc and cached.
prompts
Prompts: connections no rule decides, held until a client answers or the prompt times out.
push
The node’s push gateway (plan §8.5): a snitchhiker-relay with its push service on, which wakes devices that are asleep when a prompt waits for them, and tells them when the node goes offline. The node keeps one stream open to it (ALPN snitchhiker-push/1) for as long as it runs: the stream ending is how the gateway knows the node is gone, exactly, with no heartbeats to count. On it the node says who to tell (each device’s push target, again on each change), who to wake, and why it stops, when it does.
remote
Paired devices over the network (plan §8.2, §8.3, decision 0016): pairing with one-time secrets, and the devices’ connections, served as local ones are and closed when a device is unpaired.
resolved
Names from systemd-resolved’s monitor (io.systemd.Resolve.Monitor): every answer resolved gives, including those from its cache and its /etc/hosts, which never cross the network for the DNS queue to see. A program that resolves through resolved’s library interface (nss-resolve) sends no DNS packet at all, so without this its connections would have no names.
router
Prompt routing (plan §5.5): which clients are notified of a prompt. Every admin client lists every prompt and can answer it; routing only says who is to be told.
runtime
The running daemon: the table, the attribution programs, one deciding thread per queue, and the writer.
sockets
Waiting for another service’s socket to appear (systemd-resolved’s, Docker’s), by inotify: never on a timer.
stepup
Step-up: a dangerous action asked for by a client needs more than the client’s session. polkit authorizes the client’s process for org.snitchhiker.manage (dist/polkit), which by default asks for an administrator’s password through the user’s polkit agent. The process is named to polkit by its pidfd, so its pid can’t be reused meanwhile.
store
The daemon’s state: rules, folders and the connection history, in one SQLite database.
system
The system firewall on this node: the core model, its protocol form, and the inet snitchhiker_system table it becomes.
trust
The trusted-client registry: the client binaries root registered with snitchhikerd trust-client, each pinned to its SHA-256.
webhook
Alerts delivered to a webhook (plan §5.9): each alert, as JSON, sent (an HTTP POST) to alert_webhook, signed with alert_webhook_secret_file’s secret when there is one (HMAC-SHA256 of the body, in X-Snitchhiker-Signature: sha256=<hex>, as GitHub signs its webhooks). Sent from a thread of its own: raising an alert never waits on the network. A delivery that fails is logged, not retried.
