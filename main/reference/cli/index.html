Command line

snitchhiker talks to the running daemon over /run/snitchhiker/admin.sock, which only root can open: run it with sudo. It is the daemon’s own binary, run under another name.

status

Section titled “status”

The daemon’s version, mode and policy, and its counters: rules in effect, connections decided since it started, history entries dropped because the database couldn’t keep up, prompts waiting, and connected clients (this command’s own connection included).

policy

Section titled “policy”
Command
policy The policy in effect, marking the settings a client changed
policy set <setting>=<value>... Change settings while the daemon runs: mode=enforce|monitor, no_match=ask|allow|deny|reject, no_client=…, on_timeout=… (allow, deny, reject), prompt_timeout_secs=<5–3600>, retention_days=<1–3650>
policy reset [<setting>...] Return settings (all, without names) to daemon.toml’s

alerts

Section titled “alerts”
Command
alerts [--all] Alerts not acknowledged yet; --all: the newest 50 of any state
alerts ack <id>..., alerts ack --all Acknowledge alerts, for every client
alerts rules The alert rules
alerts rules add <name> [--query <q>] [--threshold <n>] [--window <secs>] [--first-program] Add one
alerts rules rm <id> Delete one

system

Section titled “system”
Command
system The system firewall: on or off, its policies and rules
system on, system off Turn it on or off
system input <accept|drop>, system forward <accept|drop> Its policies
system export, system import <file> [--trial <secs>] As TOML; with --trial, an import reverts by itself unless confirmed
system confirm Keep a change made with --trial

rules

Section titled “rules”
Command
rules List the rules: id (- for locked ones), action, tier, folder path and name, and conditions
rules add <allow|deny|reject> [conditions] [--name <n>] [--tier <override|normal|fallback>] Add a rule
rules rm <id> Delete a rule
rules move <id> <folder> Move a rule to a folder (0: the top level)
rules enable <id>, rules disable <id> Switch a rule on or off
rules edit <id,id,...> <change> Change many rules as one batch (one undo): enable, disable, delete, move <folder>, action <allow|deny|reject>, expires <hour|half-day|until-restart|never>
rules lint [--days <n>] The rules check; with --days, also rules that decided nothing in that many days
rules import <file> Add the rules of a rule file, in a new folder (named by the file’s [folder], or after the file)
rules export Print the stored rules as a rule file
rules import-opensnitch [<dir>] [--dry-run] Import OpenSnitch’s rules (default /etc/opensnitchd/rules) into a folder OpenSnitch; see Moving from OpenSnitch

Locked rules (the System folder and the files in rules.d) can’t be deleted, switched or changed from here.

Conditions of rules add, all of which must hold; repeat an option for alternatives:

Option
--exe <path> The executable: a path, glob:… or re:… (patterns)
--host <name> A host name, or *. and a domain
--net <cidr> An address, a range, or an alias (loopback, lan, multicast, imds, cgnat)
--port <n[-m]> A port or a range
--uid <n> A user id
--protocol <tcp|udp|icmp|icmpv6|n> The IP protocol
--any-context Also for processes in containers and other namespaces

folders

Section titled “folders”
Command
folders List the folders, with their path and how many rules each holds
folders add <name> [--parent <id>] Add a folder
folders rm <id> Delete a folder, the folders in it and all their rules. More than 20 rules is a dangerous action

explore

Section titled “explore”

The connections of the last n hours (24 by default), grouped by program (the default), host, port or user, busiest first, with how many were allowed and blocked and their bytes. --where narrows them to one program, host (empty: no name), port or user: --by host --where program=/usr/bin/curl lists where curl connects. The answer comes from hourly rollups, so it takes as long for a month of history as for an hour.

connections and kill

Section titled “connections and kill”

connections lists the live TCP connections and connected UDP sockets: state, local and remote ends, user, program (? for sockets whose opening the daemon didn’t see: inbound ones, and ones older than the daemon), the name the program looked up for the remote end, and bytes. kill closes one as a reject does: the program’s next call on it fails with ECONNABORTED.

history and undo

Section titled “history and undo”

history lists the changes to rules and folders, newest first (50 by default): id, batch, time, who made it (cli, desktop, a prompt answered from either) and what changed. undo undoes every change of a change’s batch, as a new batch; it is refused when something it would put back was changed again since. See Rules.

events

Section titled “events”

The newest connections (50 by default): sequence number, action, user, program, destination (the name the program looked up, or the address), port, protocol, and the bytes sent and received so far. With --query, only those the query matches, looked for among the newest 100 000.

explain

Section titled “explain”

Why a recorded connection (by its sequence number, from events) is decided as it is: every rule that matches it under the rules in effect now, in precedence order, the deciding one first, with each rule’s action, tier and specificity. With none, the connection would be prompted for, or decided by no_match. Rules on command lines or parent processes can’t be checked, since the history doesn’t keep those; the answer says so when such rules exist. The desktop app’s Events page has the same as the info button on each row (or a double-click on it).

learn

Section titled “learn”

Prints a rule file with a rule for each program, destination and port that no rule decided in the last n hours (default 24), in a folder named name (default “Learned”). Program paths are generalised as in prompts. Review it, then rules import it.

prompts

Section titled “prompts”
Command
prompts The prompts waiting for an answer, each with its numbered suggestions
prompts watch Print prompts as they open and as they are resolved, until interrupted. While it runs, the daemon has a client to ask
prompts answer <id> <allow|deny|reject> [--suggestion <n>] [--duration <d>] [--folder <id>] Answer a prompt with a rule made from suggestion n (default 0, the narrowest), in the program’s folder (Apps/<program>) or the folder given

Durations: once (no rule), restart, hour, 12h, forever (default). See Prompts.

audit

Section titled “audit”

The dangerous actions clients asked for, newest first (50 by default): id, time, outcome (authorized, refused, or unchecked for root’s requests and with step-up off), client, user, process, and what was asked. See Security.

version

Section titled “version”

Prints the version.

snitchhikerd

Section titled “snitchhikerd”

The daemon, started by its systemd unit. --config reads another configuration file than /etc/snitchhiker/daemon.toml. SIGHUP (systemctl reload snitchhikerd) reads the rules again; SIGTERM and SIGINT stop it. Logs go to the journal; RUST_LOG sets their level (info by default).

Trusted clients

Section titled “Trusted clients”

trust-client registers a client binary for the client socket, pinned to its SHA-256; run it again after the binary is upgraded (packages do it from their install hook). The binary must be owned by root, in directories only root can write to, and setgid to client_group. untrust-client removes it, and trusted-clients lists the registered binaries and those in trusted_clients.

The registry is a file next to the database, read whenever a client connects: changes apply to the next connection, and the daemon needn’t be running. See Security.
